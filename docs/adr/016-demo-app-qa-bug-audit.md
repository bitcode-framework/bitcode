### Charts Canvas Rendering (COMPLETE)

**Status**: Charts now render (15 canvases, 47 echarts instances, 0 errors).

**Root cause**: Echarts v6 + Vite optional peer dep bundling. Dynamic
`import('echarts')` in Vite production build resolves to
`{ default: <namespace> }` but `mod.default.init` is also `undefined`.
Static `import * as echarts` fails at Rollup build time:
`"init" is not exported by "__vite-optional-peer-dep:echarts:@bitcode/ui"`.

**Fix**: Dependency injection loader pattern (ADR-016 Decision 5).
BcChart no longer hardcodes `import('echarts')`. Instead, it calls
`loadEcharts()` from `@/core/echarts-loader`. The consumer registers the
loader ONCE at app startup:
```ts
setEchartsLoader(() => import('echarts'));
```
This works across all bundlers (Vite, Webpack, Rollup), supports CDN
loading (`setEchartsLoader(async () => window.echarts)`), and is testable.

## Context

A full browser QA pass of both demo apps (`packages/ui/demo-app` for React,
`packages/ui-flutter/example` for Flutter) revealed a large number of broken,
visually broken, or stub-only components. This ADR categorizes every finding
into severity tiers with root cause and fix plan.

## React Demo Findings

### CRITICAL — Charts do not render (0 canvas, 0 SVG, 0 echarts instances)

**Root cause**: Mitosis compiler bug — `ref={state.containerRef}` in `.lite.tsx`
compiles to `ref={containerRef}` in React output, but `containerRef` is a
`useState` value (`const [containerRef, setContainerRef] = useState(() => null)`),
not a `useRef`. React's `ref` attribute needs either a `useRef` object (with
`.current`) or a callback ref. The state value is always `null`, so echarts
never initializes.

**Affected**: `BcChart.lite.tsx` and all 23 chart-type wrapper components
(`BcChartBar`, `BcChartLine`, `BcChartPie`, etc.).

**Fix options**:
1. (Preferred) Mitosis compiler fix: when compiling `ref={state.xxx}` to React,
   emit `ref={setXxx}` (callback ref) instead of `ref={xxx}`.
2. (Workaround) Post-build script: regex-replace `ref={containerRef}` →
   `ref={setContainerRef}` in chart output files.
3. (Manual) Rewrite BcChart as a non-Mitosis `.tsx` file using `useRef`
   directly, bypassing the compiler.

### CRITICAL — Overlays render without backdrop/portal

**Root cause**: Overlay components (`BcDialog`, `BcDrawer`, `BcPopover`,
`BcTooltip`) render their `fixed inset-0 z-50` wrapper **inside** the demo
component inline rather than via `ReactDOM.createPortal`. The wrapper inherits
the parent's overflow/bounds, resulting in:
- `offsetHeight: 118px` instead of full viewport height.
- No dark backdrop (`rgba(0,0,0,0)` background).
- Dialog content is visible but appears inline, not centered over the page.

**Fix options**:
1. (Preferred) Add `createPortal` to overlay components in Mitosis source
   (wrap the overlay content in a portal to `document.body`).
2. (Alternative) Fix the demo to wrap overlay children in a portal host.

**Symptom**: "Open Contact Lookup" button clicked, but no modal appears.
**Root cause**: Same overlay portal issue as above (dialog renders inline
inside the demo card, invisible to user).

## Flutter Demo Findings

### CRITICAL — Data/Display section crashes: "Vertical viewport was given unbounded height"

**Root cause**: `data_section.dart` line 17 uses `ListView` as its root widget.
When this section is rendered inside `SingleChildScrollView` (added in
`main.dart` to fix the previous RenderFlex overflow), the `ListView` gets
unbounded vertical constraints, causing a crash.

**Fix**: Change `data_section.dart` root from `ListView` to `Column` (since
the parent `SingleChildScrollView` already provides scrolling). Same fix likely
needed for `display_section.dart` if it also uses `ListView`.

### MEDIUM — Overlays section: "ListTile background color or ink splashes may be invisible"

**Root cause**: `ListTile` widgets inside `BcBox` (which has a `DecoratedBox`
with background color) cause Flutter's assertion: ListTile's ink splash is
hidden by the parent's background. ListTile needs to be wrapped in its own
`Material` widget.

**Fix**: Wrap `ListTile` in `Material(color: Colors.transparent, child: ListTile(...))`
or restructure to avoid nesting ListTile inside BcBox with background.

### NOT FULLY REVIEWED

The Flutter demo's Forms, Overlays, Layout, Navigation, and Misc sections
were not individually reviewed due to Flutter web's canvas-based rendering
being difficult to inspect via DOM. The widget test confirms sections 0 (Forms)
and 1 (Overlays) render without `ErrorWidget`, but section 2 (Data/Display)
crashes.

### Decision Updates (2026-06-28, post-implementation)

During implementation, three architectural decisions were made that supersede
or refine the original fix options:

#### Decision 1: BcChart ref — source-level `useRef`, not compiler patch

**Original plan**: Fix the Mitosis compiler to emit `ref={setXxx}` (callback
ref) when compiling `ref={state.xxx}`.

**Decision**: Do NOT patch the compiler. Instead, migrate DOM refs and
mutable handles (timers, echarts instances) from `useStore({ xxxRef })` to
`useRef<T>(null)`.

**Scope**: All 6 affected components migrated:
- `BcChart` (`containerRef`, `instanceRef`)
- `BcAffix` (`placeholderRef`)
- `BcSignature` (`canvasRef`)
- `BcHoverCard` (`openTimerRef`, `closeTimerRef`)
- `BcViewEditor` (`textareaRef`)
- `BcFieldDynLink` (`debounceTimerRef`)

**Guardrail**: A permanent lint rule (`scripts/lint-no-usestore-refs.mjs`,
wired into `prebuild`) rejects any new `useStore({ xxxRef/xxxTimer })`
pattern. This makes the migration future-proof — no new component can
reintroduce the bug.

**Rationale**: Mitosis already compiles `useRef` correctly to React `useRef`
with auto-`.current` access (verified in `BcSplitter`). Using `useRef` is the
semantically correct Mitosis idiom for DOM refs and mutable values that should
not trigger re-renders. The `reformat-react-output.mjs` callback-ref visitor
(commit `464e46f`) remains as a safety net for any future `useStore`-based
refs that slip past the lint rule, but new code should use `useRef`.

**Consequence**: The `useState`-based ref pattern (`useStore({ xxxRef: null })`)
is now a **build error**. Any component using it must be migrated to `useRef`.
The lint rule catches the pattern at the `useStore` property-name level
(anything ending in `Ref` or `Timer`).

#### Decision 2: Overlay portals — post-build Babel AST, not source-level

**Original plan**: Add `createPortal` to overlay components in Mitosis source.

**Decision**: Implement `createPortal` injection as a post-build Babel AST
visitor in `reformat-react-output.mjs`.

**Rationale**: Portal logic is web-only (React DOM). Adding it to Mitosis
source would break RN/Flutter output (those platforms have their own overlay
mechanisms via `.native.tsx` overrides). The post-build transform runs only
on `output/react/src/` and is guarded by SSR checks (`typeof document !==
'undefined'`). This keeps the Mitosis source framework-agnostic while
ensuring overlays render correctly in web.

**Consequence**: New overlay components that use `fixed inset-0` class pattern
are automatically covered. Components with non-standard positioning (e.g.,
`fixed top-4 right-4` like BcToast) are NOT auto-detected but now work
because of the `@source` Tailwind fix.

#### Decision 3: Library Tailwind consumption contract — `@source` directive

**Problem**: Tailwind v4 auto-scanning only scans the consumer project's
source files. Utility classes that exist solely in `@bitcode/ui`'s compiled
output (`output/react/src/`) are never detected, resulting in missing CSS
rules for `absolute`, `inset-0`, `z-50`, `h-2.5`, `grid-cols-7`,
`shadow-md`, `z-[100]`, and dozens more.

**Decision**: Consumers MUST add a `@source` directive to their Tailwind CSS
entry file to scan the library's compiled output:

```css
@import "tailwindcss";
@source "../node_modules/@bitcode/ui/output/react/src";
```

This is documented per Tailwind v4's official guidance for external libraries
built with Tailwind.

**Rationale**: This is the Tailwind-recommended approach for consuming
external libraries. It is a one-time setup per consumer and fixes all
class-generation issues globally rather than per-component.

**Alternative considered**: Ship pre-built CSS with the library. Rejected
because it would prevent consumers from customizing tokens (the library's
token layer is designed to be overridden by consumers via CSS variables).

**Consequence**: This is now a **mandatory consumer setup step**. Failure to
add `@source` will result in broken layouts (zero-height elements, missing
positioning, missing z-index). This must be documented in the library README
and installation guide.

**Migration path**: If the library later adopts CSS-in-JS or ships a
pre-compiled stylesheet, the `@source` directive can be removed. Until then,
it is required.

#### Decision 4: BcSplitter contract alignment pattern (standardized)

Following the BcTabs fix (`5fb56c8`), BcSplitter was aligned to its contract
using the same pattern. This establishes a **standard contract-alignment
recipe** for any component whose implementation has diverged:

1. Contract is the source of truth (ADR-008).
2. Implementation gains: controlled prop + uncontrolled default + typed
   change handler with `BcChangeMeta<TReason>`.
3. Legacy props kept as aliases for backward compatibility.
4. Test assertions updated to match new state accessor names.
5. Demo updated to showcase the contract API (not the legacy one).

Any future contract-divergent component should follow this exact recipe.

#### Decision 5: ECharts loader — dependency injection (not hardcode import)

**Problem**: Vite treats echarts as an optional peer dep and wraps dynamic
`import('echarts')` in a proxy that loses named exports (`init`,
`setOption`). This breaks all chart components at runtime. Neither static
import nor dynamic import works reliably across bundlers.

**Decision**: BcChart uses a dependency-injection loader pattern instead of
hardcoding the echarts import. A new module `src/core/echarts-loader.ts`
provides:
- `setEchartsLoader(loader)` — consumer registers the loader ONCE at startup.
- `loadEcharts()` — BcChart calls this to get the namespace.

**Resolution chain** in `loadEcharts()`:
1. Consumer-registered loader (recommended) — works with any bundler.
2. `window.echarts` (CDN script tag) — no bundler involvement.
3. SSR bail-out (returns null when `window` undefined).
4. Last-resort dynamic import (may fail under Vite prod build).

**CJS/ESM interop**: `unwrapNamespace()` handles both direct namespace
(`mod.init`) and nested default (`mod.default.init`).

**Consumer setup** (one line in app entry):
```ts
import { setEchartsLoader } from '@bitcode/ui';
setEchartsLoader(() => import('echarts'));
```

**Rationale**: This is the pattern used by production chart libraries
(react-flow, recharts adapters) to decouple from bundler peer-dep quirks.
It is:
- **Simple**: one line of consumer setup.
- **Powerful**: supports CDN, testing (mock loader), and RN adapters.
- **Platform-aware**: Flutter uses `flutter_echarts` (ADR-015), not affected.
- **Future-proof**: echarts version changes don't break the chart component.

**Gotcha**: The consumer MUST import `setEchartsLoader` from the same module
path that BcChart uses to import `loadEcharts`. Otherwise the registered
state lives in a different module instance and charts silently fail. In the
demo app, both import from `@/core/echarts-loader` (via Vite alias).
